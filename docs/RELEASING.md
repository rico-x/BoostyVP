# Сборки, подпись и публикация

## Версии

Единственный источник версии — `version.properties`: сейчас `versionName=0.0.3`,
`versionCode=7`. Для каждого нового выпуска повышайте **оба** значения.
Android сравнивает `versionCode`, не строку версии. Старые локальные 0.2.x
имели код 6; новая публичная нумерация 0.0.3 намеренно использует 7.
Тег выпуска — `v<versionName>`. Уже опубликованные теги и APK не перезаписываются.

## Архитектуры

`./gradlew :app:assembleRelease -PsplitApks=true` создаёт ARMv7 (`armeabi-v7a`),
ARM64 (`arm64-v8a`), `x86`, `x86_64` и `universal`. Обычная сборка без флага
остаётся универсальной, чтобы не менять порядок установки debug/тестовых APK.
Минимальный Android — 6.0 / API 23; отдельные APK на каждую версию ОС не нужны.
Если ABI ОС неизвестен, используйте universal, не архитектуру процессора с коробки.

Скрипт проверяет package ID, versionName/versionCode, min/target SDK, TV-признак
и реальное содержимое `lib/<ABI>/*.so`. Сборка на все ABI не означает тестирование
на всех устройствах. Устройства с 16-КБ страницами памяти отдельно не проверены;
выравнивание ZIP по 16 КБ не является доказательством совместимости всех ELF.
Публикация в Google Play/AAB этой процедурой не предусмотрена.

## GitHub Actions

- **Verify and build BoostyVP**: push/PR/manual/reusable. Проверяет Node-инструменты,
  сайт, shell-скрипты, модульные тесты, компилирует все instrumentation APK и пять
  unsigned release APK. Секретов подписи нет. На runner эти TV-тесты **не выполняются**:
  запуск на реальном ТВ — отдельная проверка, а не следствие зелёной сборки.
- **Build and publish BoostyVP**: ручной запуск только из `main`. Повторяет Verify,
  затем подписывает на отдельном runner в окружении `release`, проверяет постоянный
  сертификат, создаёт контрольные суммы и GitHub attestation. Полный набор файлов
  сначала загружается в draft release; только после успешной загрузки он публикуется.
  Для 0.0.x по умолчанию используется pre-release.
- **Deploy project Pages**: статический сайт из `site/`; без ключа подписи.
- **CodeQL analysis**: Kotlin/Java и JavaScript, push/PR/manual и еженедельно.
  Найденные проблемы требуют отдельного разбора, а не автоматически считаются исправленными.

### Закрытое окружение release

Оно допускает только ветку `main`. Там находятся четыре секрета:

| Секрет | Содержимое |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | PKCS12-файл постоянного ключа в base64 |
| `ANDROID_KEYSTORE_PASSWORD` | Пароль хранилища |
| `ANDROID_KEY_ALIAS` | Alias существующего ключа |
| `ANDROID_KEY_PASSWORD` | Пароль ключа |

Не создавайте новый ключ для очередного релиза: это сломает обновление поверх.
Секреты задаются через защищённый ввод или stdin `gh secret set --env release`;
не через аргумент с видимым значением, issue, файл репозитория или логи. Токены
Boosty и данные пользователя **не нужны**. `GITHUB_TOKEN` выдаёт сам GitHub —
отдельный персональный PAT для публикации не используется.

Ключ восстанавливается с закрытыми правами в `$RUNNER_TEMP`, удаляется до
аттестации/загрузки артефактов; артефакты содержат только разрешённые файлы.
Локальную резервную копию ключа и пароля храните отдельно от Git и публичных APK.
Публичный SHA-256 сертификата:

```text
3f86f9845707ef4d3adf3e3d81c4ee6080b9a06f570556bdd65c0a02579b1b4c
```

Это не секрет и не хеш APK: хеш APK меняется при каждой сборке. Ожидаемый
сертификат закреплён в `build-support/release-config.json` и проверяется автоматически.

## Проверка скачанного выпуска

Скачайте APK, `SHA256SUMS` и `release-manifest.json` из одного тега Releases.
Linux: `sha256sum -c SHA256SUMS`; macOS: `shasum -a 256 -c SHA256SUMS`.
Если скачан только один APK, сравните его строку, а не игнорируйте остальные ошибки.
Совпадение хеша подтверждает целостность относительно манифеста, не доверие к источнику.

Подпись: `apksigner verify --verbose --print-certs <file.apk>` из официального
Android SDK. Сверьте SHA-256 сертификата с закреплённым выше.
Происхождение: `gh attestation verify <file.apk> --repo rico-x/BoostyVP`.
Attestation связывает бинарник с workflow/коммитом, но не гарантирует отсутствие ошибок.

## Чек-лист сопровождающего

1. Прочесть изменения, проверить права и актуальность LICENSE/NOTICE/SECURITY.
2. Повысить версию и Android-код; обновить CHANGELOG и `release-notes/v<version>.md`.
3. Выполнить локальные проверки, необходимые device-регрессии и проверку обновления
   с сохранением данных; обезличить материалы. Не публиковать приватные скриншоты.
4. По явному разрешению владельца отправить код в GitHub; дождаться CI/CodeQL/Pages.
5. Запустить `Build and publish BoostyVP` из `main`; проверить все задачи и assets.
6. Скачать опубликованные файлы, повторно проверить подпись/ABI/хеши и ссылки Pages.
7. Если остался draft после сбоя — сначала разобраться с ним. Не обходить защиту
   от перезаписи существующего выпуска и не менять опубликованные бинарники молча.

Процедура повторяема; байт-в-байт воспроизводимость между разными средами не заявляется.
