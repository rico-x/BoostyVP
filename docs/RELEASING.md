# Сборка, подпись и публикация

[English](RELEASING.en.md) · [Готовность к выпуску](RELEASE_READINESS.md)

Этот документ описывает процесс. Настроенный workflow не равен выполненному
выпуску. Push, тег, загрузка в VirusTotal и публикация требуют явного запроса
владельца; подготовка документации их не разрешает.

## Версии и архитектуры

Версия — дата по UTC и номер выпуска за день: `YYYY.MM.DD.N`, N от 1 до 99.
Workflow выбирает следующий номер по тегам `v<дата>.N`; файла version.properties
нет. Параметр `version` задаёт номер явно, например чтобы обойти уже установленную
локальную `.1`: допускаются только сегодняшняя дата по UTC и номер выше занятых. `versionCode` — `YYMMDDNN` (`2026.10.25.1` → `26102501`). Без явной версии
локальная сборка получает сегодняшнюю `.0`, которая не является публичным выпуском.
Локальная проверка: `-Pboostyvp.version=YYYY.MM.DD.N` или `BOOSTYVP_VERSION`.
Учитывайте уже установленный локальный versionCode; updater требует более высокий.

```sh
./gradlew :app:assembleRelease -PsplitApks=true -Pboostyvp.version=YYYY.MM.DD.N
```

Флаг создаёт `armeabi-v7a`, `arm64-v8a`, `x86`, `x86_64` и `universal`.
Без флага сборка универсальная. minSdk 23, targetSdk 35, compileSdk 36.
Номер выше прежних локальных 0.x; обновление сохраняет данные при том же ключе.
Проверяются package/version, min/target SDK, TV-признак и реальные `lib/<ABI>`.
Пять APK не доказывают совместимость всех ТВ. ZIP alignment 16 KiB не доказывает
совместимость каждого ELF/устройства с 16-KiB страницами. AAB/Google Play не предусмотрены.

## Workflows

| Workflow | Действие |
|---|---|
| Verify and build BoostyVP | Wrapper, Node/сайт/документация, shell-проверки, JVM-тесты, debug/test APK и пять unsigned release APK; ClamAV. Instrumentation на runner не выполняются |
| Build and publish BoostyVP | Ручной запуск из main; версия, Verify, отдельная подпись, сертификат/хеши, GitHub attestation и файл происхождения SLSA, ClamAV/VirusTotal, draft → публикация → Pages |
| Deploy project Pages | Статический RU/EN-сайт для последнего опубликованного выпуска, включая pre-release; без выпуска нет ссылок APK |
| CodeQL analysis | Анализ Kotlin/Java и JavaScript; результаты разбираются отдельно |
| Dependency review / graph / Scorecard | Проверка PR-зависимостей, граф для Dependabot и оценка практик репозитория |
| Fuzzing | Jazzer-фаззинг парсеров еженедельно и в PR, меняющих их: [разработка](DEVELOPMENT.md#фаззинг) |

`dry_run` не публикует выпуск, но подписывает и отправляет APK в VirusTotal:
это **не** полностью локальная/приватная проверка. По умолчанию выпуск pre-release.
Срабатывания VirusTotal блокируют публикацию, кроме явно заданного проверенного
порога `virustotal_max_malicious`. Отчёты/контрольные суммы относятся к конкретным
файлам, не доказывают отсутствие дефектов.

## Постоянная подпись

Окружение `release` должно разрешать main и предоставлять:

| Секрет | Назначение |
|---|---|
| ANDROID_KEYSTORE_BASE64 | Постоянный PKCS12 в base64 |
| ANDROID_KEYSTORE_PASSWORD | Пароль хранилища |
| ANDROID_KEY_ALIAS | Alias существующего ключа |
| ANDROID_KEY_PASSWORD | Пароль ключа |
| VIRUSTOTAL_API_KEY | Ключ сервиса проверки APK |

Вводите секреты защищённо/stdin, не аргументами с видимым значением.
Сессии Boosty для сборки не нужны. Публикация использует выданный GitHub
`GITHUB_TOKEN`; отдельный PAT не требуется. Наличие/защиту окружения и секретов
нужно проверить перед запуском, значения в документацию/логи не выводятся.

Не создавайте новый ключ очередному выпуску. Временный ключ в RUNNER_TEMP
удаляется до выгрузки артефактов. Ожидаемый SHA-256 сертификата:

```text
3f86f9845707ef4d3adf3e3d81c4ee6080b9a06f570556bdd65c0a02579b1b4c
```

Он закреплён в [release-config](../build-support/release-config.json), не секрет
и не хеш APK. Опубликованные теги/APK не перезаписываются.

## Проверка APK

Скачайте APK, SHA256SUMS и release-manifest.json из одного тега Releases.
Linux: `sha256sum -c SHA256SUMS`; macOS: `shasum -a 256 -c SHA256SUMS`.
При одном скачанном APK сверьте именно его строку. Хеш подтверждает целостность
относительно манифеста, а не доверие к неизвестному источнику.

```sh
apksigner verify --verbose --print-certs file.apk
gh attestation verify file.apk --repo rico-x/BoostyVP
gh attestation verify file.apk --repo rico-x/BoostyVP --bundle boostyvp-v<версия>.intoto.jsonl
```

Второй вариант проверяет файл происхождения SLSA из того же выпуска, без запроса
к GitHub за attestation; workflow выпуска перед публикацией сверяет с ним каждый APK.

Сертификат должен совпасть с закреплённым. Attestation связывает файл с workflow
и коммитом, не гарантирует безопасность. Политика сайта берёт ссылки только
из реальных assets последнего опубликованного выпуска и проверяет HTTP 200.

## Порядок выпуска

1. Сверить [готовность](RELEASE_READINESS.md), права на код, main и удалённые изменения.
2. Обновить CHANGELOG и краткий двухъязычный `release-notes/next.md`.
3. Выполнить локальные проверки и разрешённые device-регрессии; сохранить
   отчёт об обновлении без потери входа/данных.
4. По явному запросу владельца отправить код и дождаться checks актуальной ревизии.
5. Проверить release environment/сертификат; по разрешению запустить workflow
   (учитывая отправку файлов в VirusTotal даже при dry_run).
6. Проверить все пять APK, SHA256SUMS, manifest, сканы и attestation.
7. Проверить Pages RU/EN, ссылки/версии, скачать APK и обновить поверх прежнего.

Откат делается исправительным выпуском с новым versionCode, не удалением
приложения и не пересозданием ключа. Нельзя выдавать прежний зелёный CI,
локальный APK или документационный скриншот за проверенный публичный выпуск.
